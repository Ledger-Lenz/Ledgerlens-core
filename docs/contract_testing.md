# Contract Testing with Pact

This document explains how LedgerLens uses consumer-driven contract testing
(Pact) to keep the `RiskScore` schema in sync between `ledgerlens-core` (provider) and
`ledgerlens-api` (consumer).

## Why Pact?

The README's "Shared Contracts" section lists `RiskScore` as a schema that must
stay byte-for-byte in sync across `ledgerlens-core`, `ledgerlens-api`, and `ledgerlens-contracts` (Rust). Historically this was enforced only by
a convention: contributors were asked to remember to update the Rust struct and
Pydantic response models in the same change set. That is fragile, especially
because the delivery mechanism between `core` and `api` is still not fixed.

Pact invertes the responsibility: the consumer (`ledgerlens-api`) records its expectations
 as a pact file, and the provider (`ledgerlens-core`) verifies that its actual
behavior still satisfies that pact on every relevant PR. A schema break thus
fails CI in the provider repository *before* merge, instead of survacing as a
runtime deserialization failure in production.

## Concepts

- *Consumer*: In our case, `ledgerlens-api` – the service that reads `RiskScore` records.
- *Provider*: `ledgerlens-core` – the service that produces `RiskScore` objects.
- `Pact file`: A JSON document describing, for each interaction, the request
  the consumer will make and the response it expects. The pact is generated by
  the consumer and published to a Pact Broker or committed to the repo.
- Provider state:: A named fixture that the provider must set up before
  verifying an interaction (e.g, "a risk score exists for wallet X with
  conformal fields"). The provider exposes an HTTP endpoint that the Pact
  verifier calls to seed the state.
- Pact Broker:: A shared server where consumer pacts are published and provider verification
  results are recorded.

## How contract testing runs in `core`

### Prerequisites

- `pact-python` (through `requirements-dev.txt` or the CI job).
- A running Pact Broker is optional; if none is configured, the test uses a
  static pact file committed at `tests/contract/pacts/ledgerlens-api-ledgerlens-core.json`.

### Running the tests

```bash
# Use the fallback pact file (no broker)
pytest tests/contract -q

# Use a Pact Broker
PACT_BROKER_URL=https://your-broker.example PACT_BROKER_TOKEN=>... pytest tests/contract -q
```

### Provider states

The provider-state app (`tests/contract/provider_states_app.py`) exposes:

- `POST /_pact/provider-states` - receives a JSON body with a `name` and seeds
  the in-memory store.
- `GET /risk_scores/{wallet}` - returns a serialized `RiskScore` for the given
  wallet.

Currently defined provider states:

| Name | Description |
|--------------------|-----------------------------------------------------------------------------|
| `a risk score exists for wallet with conformal fields` | Seeds a risk score including `score_lower`, `score_upper`, `prediction_set`, `coverage_guarantee`. |
| `a risk score exists for wallet without conformal fields` | Seeds a `5-core` type risk score with none of the conformal fields. |

## How to update the pact when `ledgerlens-api` intentionally changes expectations

1. In the `ledgerlens-api` repo, modify the consumer test that generates the pact
   (typically a `pact-python` consumer test).
2. Regenerate the pact file (Pact CLI or your test runner).
3. Publish the new pact to the broker using the Pact CLI or the `pact-broker`:
   `tool.

   ```bash
   pact-broker publish pacts/ledgerlens-api-ledgerlens-core.json \
     --consumer-app-version <version> \
     --broker-base-url $PACT_BROKER_URL \
     --broker-token $PACT_BROKER_TOKEN
   ```

2.Alternatively, if you don't have broker access, copy the new pact file over
   ``tests/contract/pacts/ledgerlens-api-ledgerlens-core.json` (or open a PR in
   `core` that embeds the updated static pact).

After that, `core`'s next PR touching `detection/risk_score.py` will run provider
 verification against the new expectations and fail if the model does not
 conform.

## CI workflow

The `.github/workflows/contract.yml` workflow triggers on any pull request that
modifies:

- `detection/risk_score.py`
- `ingestion/data_models.py`

It installs `pact-python` and `uvicorn`, then runs:

```bash
pytest tests/contract -q
```

The workflow uses a fallback static pact when no broker secrets are configured,
so forks and local contributors can still run the suite. Verification results
are only published to the broker for same-repository branches (not forks).
